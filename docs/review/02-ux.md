# UX review

Read from code only — this box is headless, so nothing here comes from looking at the app. Every
claim traces a `<Link to=` / `navigate(` / class string I read. Severities are mine.

The short version: the *conventions* are in unusually good shape (dialogs, forms, focus, tabs,
empty states are all near-uniform), the *information architecture* is sound but under-uses the
sidebar for the two verticals that get used most, and the *daily flows* have three or four specific
places where the app makes you do work it already knows how to do for you. That last category is
where the value is.

---

## Daily-flow friction — the part worth acting on

### Reading a manga chapter in the app doesn't count, and making it count double-counts
`high` | `verified` | `src/main/manga.ts:403,406-424` vs `src/main/ipc.ts:378-381`,
`src/shared/mediaProgress.ts:97`

Finishing an episode in the video player credits the checklist automatically: `markWatched`'s
`firstTime` transition routes through `checklistRepo.logProgress` (`ipc.ts:378-381`). Finishing a
chapter in the manga reader does not — `manga.ts` never imports `checklistRepo` at all;
`markChapterRead`/`markProgress` call only `syncMediaProgress` (`:423`, `:403`). So the streak the
user watches on Home does not move when they read.

Worse is the workaround. Manga is a `mediaLog` item, so the intended fix is to press Log. But
`syncMediaProgress` has already set `media_item.progress` to the chapter number
(`manga.ts:383-387`), and `logProgress` → `advanceProgress` then does `progress = cur.progress + 1`
(`mediaProgress.ts:97`). **Read chapter 5 in the reader, credit the checklist, and the library says
chapter 6.**

The design change that caused this was deliberate and its stated reason is sound (chapter rows exist
only for locally-scanned series, so detection could never cover manga read elsewhere). The cost was
that the one case the app *can* see stopped counting.
Fix: credit `logProgress` from the `manga:markChapterRead`/`markProgress` handlers on the first
`read_at` transition — the `video:markWatched` shape — and let that own the progress write for manga,
reducing `syncMediaProgress` to chapter bookkeeping. Keep the manual Log for chapters read elsewhere.

### Status, score and favorite need a full form
`high` | `verified` | `src/renderer/src/pages/MediaDetailPage.tsx:146-170`,
`src/renderer/src/pages/MediaFormPage.tsx:144`

`api.media.update` has **exactly one caller in the entire renderer** — the edit form. On a detail
page, Status (`:155`), My Score (`:156`) and the favorite star (`:146-150`) are display-only
`StatInline`/markup. Rating something you just finished is: detail → Edit → a 13-field form
(`MediaFormPage.tsx:210-383`) → change one field → scroll → Save → `navigate(-1)`. Two pure-navigation
hops for one value.

The app already has the one-click write pattern everywhere else: a theme song gets a heart
(`MediaDetailPage.tsx:804-810`), a music track gets one, a chapter gets a read toggle, and
`logProgress` gives a title "+1 episode" without leaving the page. A *title* is the one entity you
can't touch without a form.
Fix: on the detail page make Status a `PillGroup` row, Score a pill row or stepper, and the star a
toggle — each an `api.media.update` + `qk.media.detail`/`qk.media.all` invalidation, copying
`ThemeRow` at `:755-763`. Add a heart overlay to `MediaCard` for the grids.

### The most-visited page in the app has no primary action at all
`med` | `verified` | `src/renderer/src/pages/MediaDetailPage.tsx:286`, `:125-140`

`grep -c btn-primary MediaDetailPage.tsx` returns **0**. The log-progress button renders
`className="btn-ghost w-full mt-2"` — visually identical to Edit, "Add to list", "Find torrents" and
the ActionMenu trigger stacked directly above and below it. The comment at `:125-126` still says
"One filled action per screen: logging progress is the everyday one."

So the action column is five identical full-width ghost buttons with no hierarchy, on the page you
land on after every import and every card click. The convention didn't drift to *two* primary buttons
— it drifted to zero.
Fix: `btn-primary w-full mt-2` on `LogProgressButton`. One character short of free.

### "Import" on Home doesn't import
`med` | `verified` | `src/renderer/src/pages/HomePage.tsx:631-635` → `MediaListPage.tsx:122-126`

The `Import` chip on every `GlanceCard` is `<Link to={cfg.basePath}>` — the same destination as the
card title directly above it. The dialog is local state on the list page with no URL entry point, so
the user lands on a list and must find a differently-labelled "Import from {source}" button. This
repeats for all six visible media types. The `Add {singular}` chip right beside it (`:636-638`) links
straight to the actual form, which makes the inconsistency more visible.
Fix: read `?import=1` in `MediaListPage` (the `?tab=` idiom already used by `MediaDetailPage` and
`SettingsPage`) and point the chip at `${cfg.basePath}?import=1`.

### The review session's "Done" discards where you came from
`med` | `verified` | `src/renderer/src/pages/JapaneseReviewPage.tsx:346`

`Done` is a hard `Link to="/japanese"`. The two most common ways *into* a review session are the
Checklist row (`ChecklistTaskRow.tsx:34-37` → `shared/checklist.ts:59-67`) and Home's `JapaneseCard`
DoorCard (`HomePage.tsx:352`) — so the app's most-repeated daily action reliably ends somewhere the
user wasn't. Every other sub-page in the app uses `BackButton` (`navigate(-1)`).
Fix: `navigate(-1)`.

### A tracked game session is invisible everywhere except the tab that started it
`med` | `verified` | `src/renderer/src/components/GameLaunchSection.tsx:26-28,109-113`

`useGameSession()` is mounted only inside `GameLaunchSection` — nothing else imports it. Imports and
scans get a persistent Topbar pill (`Topbar.tsx:42-44` → `ActivityIndicator`); a running game does
not. Navigate away from that one Playtime tab and there is no sign a session is being tracked, and
the settled toast (`useGameSession.ts:51-58`) only fires when some instance of the hook next mounts.
The data is safe — `gameLaunch.ts` records on process exit regardless of the renderer — but the user
gets no confirmation their play counted unless they go back and look.
Fix: mount the hook next to `ActivityIndicator` in the Topbar and render the same pill shape.

### An OS-opened file silently forgets your position, and the warning that says so is on another page
`med` | `verified` | `src/renderer/src/components/OpenFileHandler.tsx:59-66`,
`src/renderer/src/lib/readerSource.ts:16,49-53`

An "Open with NaviHUB" file navigates straight into the chromeless reader/player with `mediaId` and
`chapterId` forced to `0`, so every progress save is guarded off. `WatchLandingPage.tsx:26` already
carries exactly the right sentence — "Nothing is saved for one-off files… attach a folder if you want
resume positions" — and this flow never visits that page. The only way to learn the rule is to lose
your place.
Fix: show the same line as a dismissible strip in the reader/player when `mediaId === 0`.

### The gacha Play card promises tasks that are three navigations away
`low` | `verified` | `src/renderer/src/pages/HomePage.tsx:409-416`

"N game tasks waiting" links to `/gacha`, a grid of game cards. From there: spot the due badge
(`GachaHomePage.tsx:76-83`), click into the game, click the Coach pill (`GachaGamePage.tsx:117`), and
the reminders are in the chat thread. Three hops for a card whose label implies one.
Fix: link the card straight to `/gacha/fgo/coach` when exactly one game has due counts.

### The empty-results state points at a control that isn't rendered
`low` | `verified` | `src/renderer/src/pages/MediaListPage.tsx:304-308` vs `:288-297`

"Nothing matches these filters — clear a chip" renders whenever a search returns nothing, but the
"Clear all" control lives inside `{nFilters > 0 && …}` and `nFilters` doesn't count the search box
(`:82`, `:232`). Search for a typo with no filters active and the guidance names a button that is not
on screen.
Fix: include a non-empty search in `nFilters`, or branch the empty-state copy on it.

## Information architecture

### Only one route is genuinely undiscoverable
`low` | `verified` | `src/renderer/src/pages/NowPlayingPage.tsx`, `components/NowPlayingBar.tsx:41,68,187`

`/now-playing` is linked only from `NowPlayingBar`, which returns `null` when nothing is playing
(`:41`). It is not in the sidebar and not in the command palette. There is no way to open the
full-page player except by first starting playback. Everything else in ~94 routes reaches a real
entry point once you follow the actual link graph — including the four English test pages and
`/japanese/leeches/drill`, which look orphaned from the sidebar/palette but are one click from their
hubs. That is a good result for an app this size.

### The sidebar under-serves exactly the sections used most
`med` | `verified` | `src/renderer/src/components/Sidebar.tsx:166-195`

- **Japanese: 5 children for ~30 routes.** The hub closes the gap, so nothing is unreachable — but
  `Guide` (a read-once reference page) holds a sidebar slot while `/japanese/mine`, the action the
  codebase's own commentary describes as happening constantly while reading, is in neither the
  sidebar nor within one click of anywhere except the hub. Swap them.
- **English: 3 children for 8 routes**, and the three chosen are Dictionary/Review/Writing — the four
  *tests* that the section exists for have no sidebar presence and (see below) no palette rows either.
  `Writing` is the least-frequent activity in the section and has a slot; the vocab quiz has none.
- **Programming: 2 children for 5 routes** — correct as-is, the remainder are per-course pages.

### The command palette is 22 Japanese rows and 4 English ones
`low` | `verified` | `src/renderer/src/components/CommandPalette.tsx:46-77`

`/english/vocab`, `/english/spelling`, `/english/reading` and `/english/mechanics` have no rows.
Neither do `/quiz/song`, `/quiz/tournament`, `/now-playing`, `/search`, or the six people-browse
routes. These are pure data additions.

### Home: what's missing and what's coasting
`low` | `verified` | `src/renderer/src/pages/HomePage.tsx`

Missing, all from data Home already fetches or could cheaply:
- **Weekly checklist items.** `ChecklistCard` reads only `data.daily` (`:315`); `ChecklistStatus.weekly`
  rides the same query and is never shown. "3 of 5 done today" with no hint that a weekly item is open.
- **A running game session** (above).
- **Programming** has no presence at all — no card, and `LibraryGlance` only enumerates `MEDIA_CONFIGS`.
  Defensible if it isn't meant to be daily, but Japanese and English both got cards.

Coasting:
- **`LibraryGlance`** (`:595-642`) re-lists all seven media types with counts and chips at the bottom
  of a page whose top two-thirds is "what should I do now" — a duplicate of the always-visible sidebar,
  and the home of the broken Import chip.
- **`TopPeople`** (`:511-566`) is a genuinely nice one-time "your taste" view whose rankings barely
  move day to day, taking a full-width card plus a scroll rail on every visit. It also vanishes
  entirely below 3 voice actors (`:522`), taking the studios row with it.

## Consistency audit

A sweep of all 79 pages and ~101 components against the documented conventions. Headline: **dialogs,
forms, focus styling, tabs and empty states are near-uniform**; the misses cluster in two places.

### Dialog rules — 12 of 14 true modals fully compliant; the misses are both readers' end-of-content overlays
`med` | `verified`

- `src/renderer/src/pages/MangaReaderPage.tsx:676-677` — the end-of-chapter overlay uses
  `onClick` on the backdrop plus `onClick={(e) => e.stopPropagation()}` on the panel: **the exact
  anti-pattern the convention was written to replace**. It is also `z-30` not `z-50`, and the card has
  no `role="dialog" aria-modal="true" tabIndex={-1}` and no `useDialog`. I read these lines; the
  report is accurate.
- `src/renderer/src/pages/BookReaderPage.tsx:421-426` — backdrop dismissal is correct here
  (`onMouseDown` + target check), but same `z-30` and same missing role/aria/tabIndex.
- `src/renderer/src/components/Lightbox.tsx:60` — `aria-label="Close viewer"` where the convention is
  the literal `"Close"`.
- `src/renderer/src/components/reader/ShortcutHelp.tsx:20,23-27` — `z-40` not `z-50`, and it declares
  `role="dialog" aria-modal="true"` while deliberately skipping `useDialog`, so opening it never moves
  focus into the panel. Either adopt `useDialog` or drop the modal ARIA — claiming `aria-modal` while
  leaving background reader controls tabbable is the worst of both.
- `src/renderer/src/components/video/SubtitleTrackMenu.tsx:77-79` — `role="dialog"` on something that
  behaves exactly like a menu. Cosmetic; `role="menu"` fits.

`low` | `verified`

The two that matter because of reach:

### What's actually good here

- **12 of 14 true modals are 100% compliant on all five dialog rules** — `useDialog`, `z-50`,
  `onMouseDown`-on-overlay dismissal, `✕`/`aria-label="Close"`, `role`/`aria-modal`/`tabIndex`. Files
  written for unrelated features (`ImportDialog.tsx:34,63-84`, `gacha/GachaUnitDialog.tsx:25,74-91`)
  are structurally identical.
- **Focus styling is completely centralized**: a grep for `focus:ring|focus-visible:|focus:outline`
  across all renderer files returns **zero** hits outside the single rule at `styles.css:56`. Nothing
  fights it.
- **`PageHeader` is at 65/79 pages**, and the 14 exceptions are all legitimate (chromeless readers,
  the Home hero, and the entity-detail pages that use `EntityHeader`/`MusicEntityHeader` instead).
  Three of four form pages have zero deviations, including a comment explaining why there's no Cancel.
- **`EmptyState`'s "hide the header button with the same verb" rule holds across all 29 files** that
  use it, and no screen renders two `btn-primary`s at once — every file with several gates them by
  tab or phase.
- **Every `activeTab`/`setTab` in the app routes through the shared `Tabs` component** — eight pages,
  no hand-rolled tab bars left.

## Keyboard & accessibility

Calibrated for one person on a desktop with a keyboard and a mouse, not for screen-reader conformance.

### Zero shortcut collisions
`verified` — worth stating plainly, because with three immersive surfaces, a global palette, a player
and a dozen drills all binding keys, collisions were the likely finding. Four near-misses were
investigated and each is correctly guarded: the palette's bare `/` against typing drills, MiningPanel
inputs against reader shortcuts (both an `HTMLInputElement` guard *and* per-input
`stopPropagation`), `SubtitleTrackMenu`'s capture-phase Escape against the player's cascade, and
`ActionMenu`'s Escape against `useDialog`'s (they never nest).

All three Escape cascades are single ordered if/else chains in one `window` handler — the right shape.
`MangaReaderPage.tsx:459-467`, `BookReaderPage.tsx:326-334`, `VideoPlayerPage.tsx:553-563`, the last
correctly checking `document.fullscreenElement` first because the browser also handles Escape natively.

### Mouse-only destructive actions
`high` | `verified` | `src/renderer/src/pages/MediaDetailPage.tsx:538-546,608-616,644-652`,
`src/renderer/src/components/MediaImagesSection.tsx:98-108`

"Remove cast member", "Remove character" and "Remove image" are `hidden group-hover:flex` /
`group-hover:block` with **no `group-focus-within`** variant. A `display:none` element cannot be
focused, so these are unreachable by keyboard. The correct pattern already exists in this repo:
`QueuePanel.tsx:179` uses `group-hover:flex group-focus-within:flex`. The same three buttons also
carry `title` with no `aria-label`, against the codebase's own rule.

### The image gallery has no keyboard path at all
`med` | `verified` | `src/renderer/src/components/MediaImagesSection.tsx:82-85`

The tile that opens the Lightbox is a plain `<div onClick>` with no `role`, `tabIndex` or `onKeyDown`.

### Contrast: `gray-500` is the one "readable" shade that doesn't clear AA
`med` | `verified` | `src/renderer/src/styles.css:26`

Computed from the real `:root` values (and cross-checked against the file's own header comment, which
is accurate to two decimals):

| Combination | Ratio | AA (4.5:1) |
| --- | --- | --- |
| `text-gray-400` on base-900 | 7.70:1 | pass |
| `text-gray-500` on base-900 | **4.40:1** | fails narrowly |
| `text-gray-500` on `.card` (base-800) | **4.12:1** | fails |
| `text-gray-600` on base-900 | **2.87:1** | fails badly |
| `.kbd` (`text-gray-600` on `bg-base-700/70`) | **≈2.4:1** | fails badly |
| `text-accent/60` on base-900 | **4.46:1** | fails narrowly |
| `bg-accent` + the `text-white` override → base-900 | 10.88:1 | pass |

`gray-500` is the app's most common secondary-copy colour. Nothing here needs fixing for one
self-selecting user — but `.kbd` at 2.4:1 is the app's **only** shortcut-discovery surface (quiz
option hints, `ShortcutHelp`'s whole key list, the review setup's "Space to flip · 1 Again…" line),
which is a bad place for the least legible chip in the palette.

### Other unlabelled glyph buttons
`low` | `verified` | `MediaDetailPage.tsx:410-419,944-949`, `MediaFormPage.tsx:388-393`,
`SettingsPage.tsx:1712-1722` (`↑`/`↓`/`×` status reorder), `MusicTrackRow.tsx:100-108` (`♥`/`♡` has
`title`, no `aria-label`).

### Deliberately not flagged
The three mining surfaces — `SubtitleOverlay.tsx:111-122`, `OcrOverlay.tsx:47-71`,
`BookContent.tsx:102-113` — are all click-a-word-under-the-pointer interactions. You cannot tab to a
word you haven't identified yet. Consistent across all three, and correctly so.

### What's actually good here

- **`useDialog` (`lib/hooks.ts:45-66`) does the right four things**: moves focus into the panel unless
  focus is already inside (deferring to an inner `autoFocus`), Escape closes, and it *restores focus to
  the opener on unmount*. It does not implement a Tab trap — the only real gap given `aria-modal` is
  claimed on 15 components, and a minor one for this app.
- **Popovers correctly never steal focus** — `ActionMenu`, `QueuePanel`, `BookSettingsPopover`,
  `SubtitleTrackMenu` were all grepped for `autoFocus`/`.focus()`: none.
- **All six `@keyframes` in `styles.css` are inside `@media (prefers-reduced-motion: no-preference)`**,
  and `BootSequence.tsx` skips its own mount at module level for reduced-motion users — that is a
  better answer than animating-but-shorter.
- **Every quiz option, drill button, transport control, chapter row and TOC entry is a real
  `<button>`/`<Link>`** — a structural sweep for `onClick` on `div|li|span|img` without `role`/`tabIndex`
  found 7 hits total, of which 5 are backdrop dismissals or the reader's page-turn zone (which has full
  arrow-key equivalents).
