## Packaging (electron-builder)

**Packaging (2026-07; native boundary upgraded 2026-09-04):** electron-builder config lives in `electron-builder.yml`. The app is pinned to Electron 44.2.0 (Node 24.20) and better-sqlite3 13.0.3. better-sqlite3 13 bundles N-API binaries for Linux and Windows x64, so `npmRebuild` remains off and neither install nor `scripts/dist-win.sh` mutates `node_modules`; the local Windows cross-build only needs the wine image for NSIS uninstaller generation. `npm run test:native` performs a real write, close, reopen, read and integrity check inside Electron. Both CI build legs run it, and the Windows package additionally asserts `dist/win-unpacked/resources/app.asar.unpacked/node_modules/better-sqlite3/prebuilds/win32-x64.node` has an MZ header. The packaged Linux directory was also proven with its own Electron executable and ELF native binary. Two paths are asar-aware and must stay so: the kuromoji dict (tokenizer.ts, asarUnpack + `.replace('app.asar','app.asar.unpacked')`) and the window icon (index.ts, `process.resourcesPath` when packaged). `productName` lives ONLY in electron-builder.yml — adding it to package.json would change the userData folder name. Development and release installs require Node 22.12 or newer; CI uses Node 24.

## CI/CD — the release workflow

**CI/CD (2026-07-25; manual trigger since 2026-08-31):** `.github/workflows/release.yml` tests, packages and publishes only when manually started with **Run workflow** in GitHub Actions — ordinary pushes do not consume Actions minutes or create releases. Installers come from GitHub Releases, not from a local build. The version is **derived, never committed**: `minor = BASE_MINOR + (git rev-list --count HEAD − BASE_COMMITS)`, with the two baselines as workflow `env` pinning "7 commits = 0.2.0", stamped in by `npm version --no-git-tag-version` at build time. So the committed `package.json` version is stale BY DESIGN, and 0.x grows forever (0.9.0 → 0.10.0). `actions/checkout` must keep `fetch-depth: 0` — a shallow clone makes the commit count 1 and every release gets the same version. Jobs: `verify` (typecheck + native/main/renderer tests; also the single source of the version, via a job output) → `build` matrix (`ubuntu-latest` → AppImage, `windows-latest` → NSIS + portable; each repeats the native smoke on its target OS) → `release` (`gh release create`, re-run safe against an existing tag). Windows builds natively and packages the bundled `win32-x64.node`; the MZ-magic assertion catches a wrong-platform artifact before upload. `scripts/dist-win.sh` remains the laptop-local wine path. `SYNC_PROTOCOL_VERSION` is unrelated to the package version and must never be auto-bumped. **When Actions can't run** (credit exhausted — how v0.15.0–v0.17.0 shipped), the whole pipeline runs locally: the `/local-release` skill (`.claude/skills/local-release/SKILL.md`) is the authoritative checklist (derived version stamp → verify → AppImage → dist-win.sh w/ PE32+ check → `gh release create` with all five assets incl. both updater manifests → `/releases/latest` sanity check → stamp restore).

## In-app updates (electron-updater)

**In-app updates (2026-07-27):** Settings → System → Updates, backed by `electron-updater` against GitHub Releases. Three packaging facts are load-bearing: the `publish` block in electron-builder.yml is what makes electron-builder emit `latest.yml`/`latest-linux.yml` **and** embed `resources/app-update.yml` (verified: it still does under `--publish never`, which is why CI keeps publishing via `gh`); the workflow's matrix `files` MUST keep uploading those manifests or the updater has nothing to read; and `GITHUB_OWNER`/`GITHUB_REPO` in `updater.ts` duplicate that publish block deliberately — `setFeedURL` takes the whole config or nothing, and the token can only be supplied at runtime. **The repo is private**, so updating needs a `github.token` setting (`repo` scope / Contents:read). That key is stored through `secretStorage.ts` as an OS-protected envelope, omitted from `settings:all`, read only in main through `settingsRepo.get`, and still wiped by sanitizeSql.cjs. `electron-updater` is a runtime **dependency** (externalized by `externalizeDepsPlugin`, so verify `grep 'require("electron-updater")' out/main/index.js`). Architecture mirrors musicDownload.ts: electron-updater is EventEmitter-based but this app has no push channel, so `updater.ts` collapses its events into ONE module-level status object polled via `update:status` (500ms while `checking`/`downloading`, self-gating off the polled data so a download survives navigation), with the `status.id !== id` stale-run guard and a **module-level** `lastSettled` in `lib/useUpdateStatus.ts`. Deliberately NOT `withActivity` — the shared slot clears on completion, but `ready`/`error` must stay readable after polling stops. `download()` is **fire-and-forget** (returns immediately; awaiting would hold the IPC reply open for the whole ~140MB transfer and the bar would never move). All decisions live in `updaterCore.ts` — pure, no SDK, so tests/updater.test.ts needs no electron (the coachTools.ts split). `UpdateEnvironment` is orthogonal to `state` and names the three builds that can't self-update: `dev` (not packaged), `portable` (the Windows portable target is unsupported by electron-updater — detected via `PORTABLE_EXECUTABLE_FILE`), `no-token`; they surface as an explanation, never an error. `killActiveUpdate()` is in the before-quit list. Also here: `desktopName` in package.json + `linux.syncDesktopName` set the Linux WM_CLASS so the window groups under the user's own `navihub.desktop` shortcut instead of showing as a separate generic taskbar entry — that field is safe in package.json, unlike `productName`.

## Library export

**Library export:** `scripts/sanitizeSql.cjs` is the single privacy authority for both export paths. The older `scripts/export-library.cjs` command keeps its privacy-safe default bundle, while Settings → Keys & Folders → Library export exposes section, asset and optional personal-tracking policies without requiring npm on the destination PC. New personal/tracking columns or tables MUST be added to the sanitizer and `tests/exportSanitize.test.ts` or they leak into exports.

The in-app runner in `src/main/libraryExport.ts` uses SQLite's online backup API, so an open WAL database produces one consistent copied `navihub.db`. Only that copy is sanitized. Excluded media sections cascade out before orphaned graph entities and polymorphic list entries are pruned. Spotify playlist snapshots are optional and preserve source metadata only: ordinary playlist/local scan rows are deleted and every `matched_track_id` is cleared. Managed `media/` covers and configured anime-theme `audio/` are copied only when the sanitized database still references them; local music, manga, book, video and wrestling files are never candidates.

Exports are assembled beside the chosen destination as an unmistakable partial path, then atomically renamed to a unique timestamped folder or ZIP. ZIP uses the packaged `archiver` dependency in streaming store mode, so large bundles do not enter renderer or main-process memory. Destination checks reject NaviHUB's data and theme-audio source trees, and a best-effort free-space check accounts for both staging and ZIP output. Cancellation is available through the dialog and Tasks, removes partial output, and is called before database teardown on quit. `libraryExport:status` is polled; there is no push channel. A successful result remains in module state for the app session and includes `README.txt` plus a non-sensitive JSON manifest.
