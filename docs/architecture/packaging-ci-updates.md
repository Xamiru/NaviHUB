## Packaging (electron-builder)

**Packaging (2026-07):** electron-builder config in `electron-builder.yml`. Windows cross-builds have two traps, both handled by `scripts/dist-win.sh`: NSIS uninstaller generation needs wine (so electron-builder runs inside the `electronuserland/builder:wine` docker image), and `@electron/rebuild` can't cross-fetch native modules for another OS — it silently keeps the Linux `better_sqlite3.node` (so the script swaps in the win32-x64 prebuild first; `npmRebuild` is off in the yml). After any Windows build, verify with `file dist/win-unpacked/resources/app.asar.unpacked/node_modules/better-sqlite3/build/Release/better_sqlite3.node` → must say PE32+, not ELF. Two paths are asar-aware and must stay so: the kuromoji dict (tokenizer.ts, asarUnpack + `.replace('app.asar','app.asar.unpacked')`) and the window icon (index.ts, `process.resourcesPath` when packaged). `productName` lives ONLY in electron-builder.yml — adding it to package.json would change the userData folder name.

## CI/CD — the release workflow

**CI/CD (2026-07-25):** `.github/workflows/release.yml` tests, packages and publishes on every push to `main` — installers come from GitHub Releases, not from a local build. The version is **derived, never committed**: `minor = BASE_MINOR + (git rev-list --count HEAD − BASE_COMMITS)`, with the two baselines as workflow `env` pinning "7 commits = 0.2.0", stamped in by `npm version --no-git-tag-version` at build time. So the committed `package.json` version is stale BY DESIGN, and 0.x grows forever (0.9.0 → 0.10.0). `actions/checkout` must keep `fetch-depth: 0` — a shallow clone makes the commit count 1 and every release gets the same version. Jobs: `verify` (typecheck + test; also the single source of the version, via a job output) → `build` matrix (`ubuntu-latest` → AppImage, `windows-latest` → NSIS + portable) → `release` (`gh release create`, re-run safe against an existing tag). **Windows builds natively**, which is why neither the wine image nor the win32 prebuild swap appears in the workflow — `npm ci`'s postinstall electron-rebuild produces a correct PE binary, asserted before upload by an MZ-magic check (the cross-platform form of the `file` check above). `scripts/dist-win.sh` is unchanged and remains the laptop-local path. In a build job NEVER reinstall node_modules after `npm ci` — postinstall would rebuild the native module. `SYNC_PROTOCOL_VERSION` is unrelated to the package version and must never be auto-bumped. **When Actions can't run** (credit exhausted — how v0.15.0–v0.17.0 shipped), the whole pipeline runs locally: the `/local-release` skill (`.claude/skills/local-release/SKILL.md`) is the authoritative checklist (derived version stamp → verify → AppImage → dist-win.sh w/ PE32+ check → `gh release create` with all five assets incl. both updater manifests → `/releases/latest` sanity check → stamp restore).

## In-app updates (electron-updater)

**In-app updates (2026-07-27):** Settings → System → Updates, backed by `electron-updater` against GitHub Releases. Three packaging facts are load-bearing: the `publish` block in electron-builder.yml is what makes electron-builder emit `latest.yml`/`latest-linux.yml` **and** embed `resources/app-update.yml` (verified: it still does under `--publish never`, which is why CI keeps publishing via `gh`); the workflow's matrix `files` MUST keep uploading those manifests or the updater has nothing to read; and `GITHUB_OWNER`/`GITHUB_REPO` in `updater.ts` duplicate that publish block deliberately — `setFeedURL` takes the whole config or nothing, and the token can only be supplied at runtime. **The repo is private**, so updating needs a `github.token` setting (`repo` scope / Contents:read) — wiped in sanitizeSql.cjs. `electron-updater` is a runtime **dependency** (externalized by `externalizeDepsPlugin`, so verify `grep 'require("electron-updater")' out/main/index.js`). Architecture mirrors musicDownload.ts: electron-updater is EventEmitter-based but this app has no push channel, so `updater.ts` collapses its events into ONE module-level status object polled via `update:status` (500ms while `checking`/`downloading`, self-gating off the polled data so a download survives navigation), with the `status.id !== id` stale-run guard and a **module-level** `lastSettled` in `lib/useUpdateStatus.ts`. Deliberately NOT `withActivity` — the shared slot clears on completion, but `ready`/`error` must stay readable after polling stops. `download()` is **fire-and-forget** (returns immediately; awaiting would hold the IPC reply open for the whole ~140MB transfer and the bar would never move). All decisions live in `updaterCore.ts` — pure, no SDK, so tests/updater.test.ts needs no electron (the coachTools.ts split). `UpdateEnvironment` is orthogonal to `state` and names the three builds that can't self-update: `dev` (not packaged), `portable` (the Windows portable target is unsupported by electron-updater — detected via `PORTABLE_EXECUTABLE_FILE`), `no-token`; they surface as an explanation, never an error. `killActiveUpdate()` is in the before-quit list. Also here: `desktopName` in package.json + `linux.syncDesktopName` set the Linux WM_CLASS so the window groups under the user's own `navihub.desktop` — that field is safe in package.json, unlike `productName`.

## Library export

**Library export:** `scripts/export-library.cjs` snapshots the live DB, strips personal data via `scripts/sanitizeSql.cjs` (shared with tests/exportSanitize.test.ts — edit them together when tables gain personal columns), and stages `navihub.db` + `media/` + theme audio + README into `~/navihub-export/navihub-bundle`. New personal/tracking columns or tables MUST be added to sanitizeSql.cjs or they leak into exports.
