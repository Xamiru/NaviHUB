## Checklist

**Checklist (2026-07-25, reworked 2026-07-27)** — `/checklist` (`ChecklistPage`, sidebar link directly under Home, plus a "Routine" card in the HomePage right rail): a daily + weekly recurring board. The CATALOG of possible items is CODE (`src/shared/checklist.ts`, `CHECKLIST_DEFS` — the `GACHA_GAMES` idiom); in-app the user can only add/remove items, retarget them and reorder them, so new KINDS are a code change. `key` strings are FROZEN (stored in `checklist_task.task_key`/`checklist_log.task_key`). Three item kinds: **mediaLog** (the checklist performs the tracking write — anime/manga/TV episodes, films), **detected** (completion is READ from tables the app already writes — `jp_review_log` distinct `card_id`, `jp_lesson.learned_at`, `quiz_session.played_at`; clicking the row navigates to where the activity happens) and **manual** (plain tick; one per gacha game, generated from `GACHA_GAMES`). **Every detected item also takes hand-made credits** (`checklist:credit`, un-clamped, one log row each, individually undoable): `progress = detected + credits`, and the streak pass mirrors that sum — v1 had no override and the user hit exactly the dead end it creates. Manga was detected from `manga_chapter.read_at` and is now mediaLog for the same reason: those rows only exist for locally-scanned series read in the in-app reader, so any other way of reading manga could never tick it (progress may then run ahead of the scanned chapter list — harmless, `manga.ts:syncMediaProgress` is monotonic).

## Progress logging is app-wide, not a checklist silo

**Progress logging is app-wide, not a checklist silo.** `@shared/mediaProgress.ts` is the single pure definition of "I watched/read another one": `advanceProgress(state, statuses, unitProgress)` does status promotion (null/planned → in-progress, last unit → completed) and, on an already-finished title, **wraps into a fresh pass** — `progress` back to 1, `rewatch_count = max(count,1)+1` (that column is *times consumed*, which is how `mediaRepo.timeStats` reads it), flagged by `startedRewatch` so callers announce it instead of silently resetting. It also owns `STATUS_FALLBACKS`/`parseStatuses` (main can't import mediaConfig.ts) and `UNIT_PROGRESS_TYPES` (mirrors `MediaConfig.unitProgress` — keep in step). `checklistRepo.logProgress(mediaId, today, task?)` is the ONE write path: with a task (checklist Log button) or without (every media detail page's log button, `media:logProgress`, labelled from `MediaConfig.logUnitLabel`), in which case it credits whatever mediaLog item covers that type, daily before weekly, or none. `payload.prior` snapshots progress/status/rewatchCount so undo restores a rewatch too.

## Tables, weeks and dates

Two tables (`checklist_task` = the enabled board incl. a nullable `target` override, `checklist_log` = events) with NO FK between them and none on `media_id` — removing + re-adding an item keeps its history, and reads LEFT JOIN + fall back to the cached title (jp_card.source_media_id precedent). `target` shipped one build later → needs its `ensureColumn` as well as the init.sql column. **Weeks run SATURDAY→FRIDAY** (`WEEK_START = 6`); `period_key` is the local day for daily rows and the week's Saturday for weekly. **Every date is computed in MAIN as a LOCAL day** and passed into the repo (`status/logProgress/tick/credit/untick` all take `today` — coachRepo's testability pattern); `ipc.ts`'s `todayLocal()` sits at the top of `registerIpc`, shared by gacha goals + checklist. The renderer only FORMATS main's date strings — never `new Date()` for a day, which is the UTC-vs-local bug the gacha coach's `CoachRail` still has. ONE read channel `checklist:status` returns board + streak + 52-week heatmap; a day is "complete" when every daily item that already existed then (`date(created_at,'localtime') <= day`) hit its (possibly overridden) target, fed to the shared `musicRepo.computeStreaks`. The board **seeds itself on first launch** (`seedChecklist` in connection.ts, `CHECKLIST_SEED`, gated by the `checklist.seeded` setting — wiped on export alongside both tables, or a recipient's board never seeds). Page/Home queries use `staleTime: 0` (+ a 60s interval on the page) so returning from `/japanese/review` re-detects and an idle page rolls over at midnight; log/undo invalidate `qk.checklist.all` + `qk.media.all`. UI is the StatsPage hero treatment (minus its glyph) over tight rows with inline progress bars; edit mode swaps in drag handles (`SortableList`/`useOptimisticReorder` — memoise the mapped rows, its re-sync effect keys on array identity), target inputs and remove buttons. `ChecklistAddDialog`'s cadence is CONTROLLED by the page (`adding` IS the cadence) — v1's local `useState(cadence)` copy is what made daily/weekly appear swapped. Picker reuses `api.media.list({mediaType, search})` (GachaGameImageDialog pattern — NOT `UniversalPicker`, whose global search caps at 20 rows across all types), floats in-progress/planned titles to the top and marks finished ones "Again". Tests: mediaProgress.test.ts (pure rules incl. rewatch arithmetic), checklist.test.ts (`process.env.TZ='UTC'`, anchored on Sat 2026-07-25).
